# Decision explanation examples

These examples correspond to actual results in
[`examples/live-demo.json`](examples/live-demo.json), generated by `scripts/demo.py`
against separate API and worker processes. IDs/timestamps naturally differ per run.
The JSON includes the full input, pinned workflow definition, hashes, rule traces,
dependency results, lifecycle transitions and reviewer reasoning.

## Approved loan (`examples.approval`)

```json
{"applicant_id":"demo-001","age":30,"income":60000,"amount":25000,"consent":true}
```

| Evaluated rule | Actual / threshold | Matched |
| --- | --- | --- |
| missing_consent | true == false | false |
| underage | 30 < 18 | false |
| income_below_minimum | 60000 < 30000 | false |
| identity_failed | verified true == false | false |
| high_risk | risk score 10 >= 80 | false |
| review_required | risk 10 >= 50 OR amount 25000 > 100000 | false |

Output: `APPROVED`. The simulated provider's result is committed under
`dependencies.identity`. Rule traces name their exact data fields and actual values.
No blocking/review rule matched, so default routing reached the approved terminal.

## Rejected loan (`examples.rejection`)

Same input with `age: 17`. `missing_consent` is false; `underage` is true.
The matched rule branches directly from eligibility to the rejected terminal.
Output: `REJECTED`. Later eligibility rules and the identity provider are not run.
The reason is traceable to `input.age`, actual 17, required minimum 18.

## Manual decision (`examples.manual_pending` / `examples.manual_approved`)

Same baseline input with `amount: 200000`. Eligibility and identity checks pass.
`review_required` matches because the amount exceeds 100000. Output pauses at
`MANUAL_REVIEW`. Reviewer `demo-reviewer` supplies decision `approve` and reason
`Verified supporting documents`. The audit records both the configured rule branch
and the human decision; final output is `APPROVED`. The engine does not represent a
human override as a successful automated check.

## Retry and recovery (`examples.retry_pending` / `examples.retry_recovered`)

Same baseline input plus `simulation: {"fail_until": 1}`. Attempt 1 produces
`provider_unavailable`, marked transient. State and `retry_scheduled` event commit
together, with a due timestamp two seconds later. The worker's second attempt uses
the same operation key, returns verified/risk=10, and produces `APPROVED`.
The audit retains both the failed and successful attempts. Eligibility rules run once.

## Permanent failure (`examples.permanent_failure`)

`simulation: {"permanent_failure": true}` produces one permanent failure and no retry
schedule. The workflow follows `identity.on_failure` to `MANUAL_REVIEW`, preserving
an explicit distinction between unavailable evidence and an adverse business rule.

## Changed rules (`examples.policy_v1` / `examples.policy_v2`)

The demo publishes a separate workflow `demo_policy_change`. Version 1 approves the
baseline input. Version 2 lowers the high-risk rejection threshold from 80 to 5;
the same simulated score of 10 now triggers `high_risk` and outputs `REJECTED`.
The v1 request keeps its original definition, hash, outcome and audit. Integration
tests additionally prove that a request paused for retry still uses v1 after v2 is
published and that original idempotency keys survive schema changes.

## Vendor onboarding (`examples.vendor_approval`)

```json
{"vendor_id":"demo-vendor","country":"IN","documents":true,"annual_spend":20000}
```

The documents rule, verification dependency, country/spend assessment and terminal
stages all use configuration, without loan-specific code in the engine.
Output: `APPROVED`. Missing documents reject; `country: OTHER` requires manual review.
